# Criterion 6 — latency cost of count-stability

**Date:** 2026-08-21 · **Criterion:** p99 within 2× the naive path, ≥5 runs, variance reported
**Verdict:** **met, but not comfortably** — worst-case 1.93× against a 2.00× threshold

## Result

| Arm | p50 | p95 | p99 | mean |
|---|---|---|---|---|
| naive (as written) | 8.83 | 11.63 | 30.44 | 8.98 |
| naive (dict lookup) — the denominator | 7.92 | 11.33 | 35.65 | 8.09 |
| **enforced** | 11.67 | 19.50 | 47.90 | 12.71 |

Microseconds. Median across 7 repeats, 4,320 paired samples per arm per repeat.

| Ratio | Median | Worst of 7 |
|---|---|---|
| p99, enforced ÷ naive | 1.41× | **1.93×** |
| p50, enforced ÷ naive | 1.47× | 1.48× |
| p99 vs the as-written naive path | 1.36× | — |

**p50 is the number to trust**: 1.46–1.48× across all seven repeats, a spread of 0.02. That is
the real cost of enforcement. p99 ranges 1.28–1.93× because a tail at 40 µs is one scheduler
interrupt wide.

**The worst case passes with 3.5% of headroom.** Stated rather than rounded away: a slower
machine, a larger corpus or a longer benchmark could put a repeat over 2.00×. The honest claim
is "the typical cost is 1.47× and the tail occasionally reaches 1.9×", not "comfortably within
budget".

## The first version of this benchmark was wrong

Measured each arm in its own block, then compared p99s. Across 7 repeats:

```
ratio 2.97x, 3.80x, 4.13x, 1.66x, 0.99x, 1.03x, 0.88x
```

Two repeats put the enforced arm **faster than naive**. That cannot be true — enforced runs
the same BM25 scoring plus 35 permission checks plus padding. An arm doing strictly more work
cannot be faster, so the measurement was noise, and the 4.13× that would have failed the
criterion was the same noise pointing the other way.

The cause: at single-digit microseconds, one context switch dominates the 99th percentile, and
each arm was measured over a different two-second window with different machine conditions.

Two fixes:

- **Paired sampling.** Both arms are timed adjacent to each other on the same principal and
  query, alternating which runs first. An interruption now lands on both arms instead of
  whichever one was unlucky.
- **An A/A control.** Two instances of the *same* arm run through the identical protocol. Its
  ratio is the harness's noise floor.

## The A/A control is what makes the number believable

| Repeat | A/A (same code both arms) | A/B (enforced vs naive) |
|---|---|---|
| 1 | 1.07× | 1.61× |
| 2 | 1.11× | 1.28× |
| 3 | 1.12× | 1.29× |
| 4 | 1.03× | 1.34× |
| 5 | 1.12× | 1.93× |
| 6 | 1.14× | 1.41× |
| 7 | 1.03× | 1.52× |

**Noise floor: median 1.11×, worst 1.14×.** Every A/B repeat exceeds every A/A repeat, so the
difference is the code and not the machine. Without this control, "1.41×" would be a number
with no way to tell whether it meant anything.

It also bounds what this harness *cannot* see: a real difference under ~1.14× would be
invisible here, whichever way it pointed.

## A fairness problem that would have flattered the result

`NaiveRetriever.search` resolves each result id with `next(d for d in documents if d.id == …)`
— a linear scan per result, O(k·n). `EnforcedRetriever` uses a dict built once in `__init__`.

Comparing them directly measures partly the defence and partly the baseline's sloppy lookup,
and that bias runs in favour of the thing being sold. So the denominator is a third arm: naive
with the same dict lookup, semantics untouched, still leaking exactly as much.

It costs 0.05× of ratio (1.41× against the fair denominator, 1.36× against the as-written one).
Small — but the size of a correction is only knowable after making it, and choosing the
flattering denominator because the difference turned out small is the same decision as choosing
it because it was large.

## Where the cost comes from

| | Permission checks per query |
|---|---|
| naive | 5 — on the top-k it already ranked |
| enforced | 35 — on the whole corpus, before ranking |

7× the checks for 1.47× the latency, because both arms pay for BM25 scoring and that dominates.

**The cost scales with corpus size, not with k.** At 35 documents it is invisible. At a million
it is a full scan per query and this implementation would need a precomputed readable set or a
permission-partitioned index. That is a limit of the approach, not of the benchmark, and it is
the first thing that would need solving before this ran anywhere real.
