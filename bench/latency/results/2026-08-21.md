# Criterion 6 — latency cost of count-stability

**Date:** 2026-08-21 · **Criterion:** p99 within 2× the naive path, ≥5 runs, variance reported
**Verdict:** **met on every statistic this harness can resolve.** Per-request p99 is reported
as **unresolved** rather than resolved to whichever run passed.

**The cost of not leaking is about 1.5× latency**, and 3.5 µs per search on this corpus.

## Per-request p99 is not measurable in-process, and saying so is the finding

The criterion asked for p99. This harness cannot deliver it honestly at this scale.

Two runs of the same code, no changes between them:

```
run A   worst-case p99 ratio  1.79×     → would have been reported as MET
run B   worst-case p99 ratio  2.79×     → would have been reported as NOT MET
```

At ~11 µs per search, one scheduler interrupt **is** the 99th percentile. The A/A control
settles it: two instances of *identical code*, same protocol, differ by up to **1.15×** at p99.
Any p99 difference below that is unmeasurable here whichever way it points, and the run-to-run
verdict swing is larger than the effect being measured.

Picking run A would have been picking a result. So p99 is reported as unresolved, and in its
place: p50 and p95, stable to ±0.03 across seven repeats, and a batched arm where the tail
genuinely resolves.

Resolving per-request p99 properly needs a quiet dedicated host, or a corpus large enough that
per-request cost exceeds interrupt latency by an order of magnitude. Both are out of scope here;
neither is hard to state.

## Three measurement bugs, each caught before the number was believed

### 1. Unpaired sampling produced an impossible result

The first version timed each arm in its own block, then compared p99s:

```
ratio  2.97×  3.80×  4.13×  1.66×  0.99×  1.03×  0.88×
```

Two repeats put the **enforced arm faster than naive**. That cannot be true — enforced runs the
same BM25 scoring *plus* 35 permission checks *plus* padding. An arm doing strictly more work
cannot be faster, so the tail was noise, and the 4.13× that would have failed the criterion was
the same noise pointing the other way.

Fixed by **paired sampling**: both arms timed adjacent on the same principal and query,
alternating which runs first, so an interruption lands on both.

### 2. The A/A control was reported one-sided

`max()` over the control ratios. But a control ratio of **0.74 is as much noise as 1.35** — the
first version called a 26% swing a "1.03× noise floor". Now reported as deviation from unity in
either direction.

### 3. Batching at 25 did not resolve the tail either

The batched arm was added to get a measurable p99, and at 25 searches per sample its worst case
came in at **1.99× against a 2.00× threshold** — a pass by 0.5%, which is not a pass, it is the
same unresolved tail at a smaller amplitude. A ~300 µs sample still lets one 20 µs interrupt
move it 7%.

Raised to 120 searches per sample (~1.4 ms, interrupt under 2%). Worst case 1.47×, spread 0.14
across seven repeats. That is a resolved tail.

**Batched p99 is not per-request p99.** Batching smooths the tail it aggregates, so it answers
"how does the enforced path's tail behave under sustained load" and not "what is the worst single
request". Labelled as such rather than presented as the criterion's number.

### And a fairness problem that would have flattered the result

`NaiveRetriever.search` resolves each result id with `next(d for d in documents if d.id == …)` —
a linear scan per result, O(k·n). `EnforcedRetriever` uses a dict built once. Comparing them
directly measures partly the defence and partly the baseline's sloppy lookup, with the bias
running in favour of the thing being sold.

The denominator is therefore a third arm: naive with the same dict lookup, semantics untouched,
still leaking exactly as much. It is worth 0.05–0.12× of ratio. Small — but the size of a
correction is only knowable after making it, and choosing the flattering denominator because the
difference turned out small is the same decision as choosing it because it was large.

A related bug the linter caught: the as-written arm's ratio was originally computed by dividing
the enforced p99 from *one* pairing by the naive p99 from *another*, discarding the adjacency
that makes a paired ratio meaningful.

## Where the cost comes from

| | Permission checks per query |
|---|---|
| naive | 5 — on the top-k it already ranked |
| enforced | 35 — on the whole corpus, before ranking |

7× the permission checks for 1.5× the latency, because both arms pay for BM25 scoring and that
dominates.

**The cost scales with corpus size, not with k.** At 35 documents it is 3.5 µs. At a million it
is a full scan per query, and this implementation would need a precomputed readable set or a
permission-partitioned index. That is a limit of the approach rather than of the benchmark, and
it is the first thing that would need solving before this ran anywhere real.

## Reproduce

```bash
python bench/latency/measure.py
```

`latency.json` carries every per-repeat ratio, the A/A control series, the batched arm and the
`per_request_p99_resolved: false` flag.
