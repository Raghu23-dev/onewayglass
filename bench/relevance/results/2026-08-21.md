# The relevance channel — count-stability is necessary, not sufficient

**Date:** 2026-08-21 · **Verdict:** **channel present.** Inference **15/15 exact**, recovered by
reading the results. No count comparison, no second principal, no timing, no statistics.

This is the most serious limitation in the project and it was found **after** all six criteria
passed, by looking at what the deployed instance actually returns to a caller.

## What was missed

Every earlier benchmark measured an **observer of the count**: a colleague comparing notes, a
proxy log, a cross-principal comparison. Against that observer, count-stability works — 17
documents revealed becomes 0, and the count is identical for all 9 principals.

But in the original threat model the attacker **is the principal**. They receive the results.
They can read them.

Production sweep, `"redundancy planning next fiscal year"`, as an engineering IC:

```
result_count: 5          ← stable, identical to the CEO's
results:      5 documents, every one flagged padded=true,
              none containing the words "redundancy", "planning" or "fiscal"
```

The count says nothing. The **contents** say everything: none of the five results answer the
question, so all five are filler, so every document that did match is one they cannot read.

## The measurement

Attacker model deliberately weaker than what is available to them: no BM25, no corpus
statistics, no second request. One question per result — *does this document share a single
non-stopword term with my query?* A document with none of them did not rank. That is checkable
by eye.

| | Count channel | Relevance channel |
|---|---|---|
| Probes where restricted documents matched | 13/15 | 13/15 |
| Inference exactly correct | **0/15** | **15/15** |
| Requests needed | 2+ (cross-principal) | **1** |
| Statistics needed | none | none |
| Precision needed | exact counts | none — read the text |

Per-probe, the inferred count matched the true number of hidden matches on **every single
probe**, including the two where the answer was correctly zero.

| Query | Available | Relevant by reading | Inferred hidden | Actual |
|---|---|---|---|---|
| compensation bands for senior engineers | 2 | 0 | 2 | 2 |
| redundancy planning next fiscal year | 3 | 0 | 3 | 3 |
| grievance case notes raised this year | 3 | 0 | 3 | 3 |
| acquisition discussions | 1 | 0 | 1 | 1 |
| security audit findings severity | 3 | 2 | 1 | 1 |
| holiday allowance annual leave | 1 | 1 | **0** | **0** |
| deployment runbook roll back | 1 | 1 | **0** | **0** |

The two zero rows matter: the channel is not merely noisy-positive. It correctly reports *nothing
hidden* when nothing is hidden, which is what makes it a reliable oracle rather than a guess.

## And the `padded` flag hands it over outright

`Result.padded` exists so an authorised caller can weight or hide filler. That is the right
design for the caller — and when the caller is the attacker, it is a direct read of the number
the count no longer gives. No inference required at all.

The flag was justified in `docs/03-architecture.md` on the grounds that "the *count* must carry
no information, not the payload". That reasoning holds only against an observer who sees the
count and not the payload. Against the recipient it is wrong, and it was wrong when it was
written.

## What the thesis pre-committed to

From `docs/02-thesis.md`, before any code existed:

> If padding cannot be made indistinguishable — for example if padded results are detectable by
> **relevance score**, position or latency — publish the residual channel and its bandwidth
> rather than claiming stability.

Three vectors named. Latency was measured (`bench/timing/`, SNR 0.73, 1.8 µs — a weak channel
needing thousands of samples). **Relevance is the strong one** and went unmeasured until the
deployment made it visible: it needs one request and no statistics, and it recovers the *full*
original inference rather than a fraction of it.

## What count-stability is actually worth

Not nothing. It closes a real channel with real attackers:

- a colleague comparing result counts on the same query
- an access log or proxy that records counts but not payloads
- an analytics pipeline that aggregates per-principal result counts
- anyone downstream of the payload who still sees the shape

Those are the cases where the count leaks and the content does not reach the attacker.

What it does **not** do is protect against the principal reading their own results. For that,
padding must be relevance-**plausible**: filler that shares query terms and reads as a
near-answer. And even then a determined reader distinguishes a real answer from a topically
similar non-answer, which is a substantially harder problem than count-stability and is not
solved here.

## Consequence for the criteria

Criteria 1–6 remain met **as written** — they measured the count channel, and the count channel
is closed. But criterion 2's phrasing, "count inference defeated", describes a narrower result
than the README originally implied. The honest claim is:

> Count-stability defeats an observer of the count. It does not defeat the recipient of the
> results.

The README and writeup now say this in place of a general claim. The threat model was too narrow,
and that is a flaw in how the problem was framed rather than in how the fix was built.
