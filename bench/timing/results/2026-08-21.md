# Kill condition 3 triggered: a timing channel survives count-stability

Count-stability closes the count channel. It does **not** close timing, and this is the
honest report that `docs/02-thesis.md` pre-committed to publishing if a channel survived.

## Result

7 repeats × 2,000 runs per arm, arm order alternated between repeats:

| Repeat | Few-match median | Many-match median | Diff | SNR |
|---|---|---|---|---|
| 1 | 12.2 µs | 10.4 µs | 1.8 | 0.42 |
| 2 | 12.2 | 10.4 | 1.8 | 0.85 |
| 3 | 12.2 | 10.3 | 1.8 | 0.84 |
| 4 | 12.1 | 10.4 | 1.7 | 0.73 |
| 5 | 12.2 | 10.4 | 1.8 | 0.54 |
| 6 | 12.1 | 10.3 | 1.7 | 1.12 |
| 7 | 12.1 | 10.4 | 1.7 | 0.42 |

**Median SNR 0.73** (range 0.42–1.12), median difference **1.8 µs**. Above the 0.5
threshold, so: **a timing channel is present.**

The medians are remarkably steady — 12.1–12.2 against 10.3–10.4 across every repeat. The SNR
varies because the *noise* varies, not the signal. That stability is what makes this a real
channel rather than an artefact.

## The direction is counterintuitive, and it matters

The heavily-padded arm is **faster**, not slower.

Padding appends documents from a pre-sorted readable list, which is cheaper than scoring more
candidates. So the channel does not leak "this response was padded". It leaks **"this query
had few readable matches for you"** — which, for a principal who knows the corpus, is close
to the same information the count used to give away.

Had I assumed padding would be slower and only tested that direction, I would have measured
the wrong arm and concluded there was no channel.

## What this does and does not mean

**Does:** count-stability is a partial defence. The count channel is closed; a timing channel
of roughly 1.8 µs remains in this in-process implementation.

**Does not:** it is not necessarily exploitable in a deployment. 1.8 µs is far below network
jitter, so an attacker over HTTP would need a very large number of observations to separate
the arms — and that volume is itself an anomalous query pattern a defender can see.

**Explicitly not claimed:** that the channel is absent. It is present and measured, and the
README says so. Constant-time retrieval is a listed non-goal, so this is a known and stated
limitation rather than an oversight.

## A measurement bug caught first

The initial version ran the experiment **once** and reported a single SNR. Across three runs
that number varied **0.26 → 0.64**, straddling the 0.5 threshold — so the verdict flipped
between "no channel" and "channel present" run to run. Reporting one run would have been
reporting a coin toss as a finding.

Fixed by taking the median of 7 repeats and alternating arm order, since always measuring the
same arm first lets cache warmth and CPU frequency scaling bias the result in one direction.

## What would close it

Padding the *execution path* rather than only the result set: score a constant number of
candidates regardless of how many are readable, discarding the unreadable ones after scoring.
That costs work proportional to the whole corpus on every query, which is the trade — and it
is why constant-time retrieval is a non-goal here rather than a quick fix.

## Reproduce

```bash
python bench/timing/measure.py
```
